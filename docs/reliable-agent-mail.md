# Agent Mail 收件、换手与迁移

本改动提供协议 v3 的两阶段收件，Claude/Codex 共用同一收件循环。v2 已用于发送端的业务身份去重，因此收件确认使用 v3。没有新增数据库列或迁移；没有自动改配置、发布服务端或启动模型。

## 收件确认

1. Agent 读取 `GET /v1/lmc/agent/channel-key` 的 `mailProtocol`。新服务端返回 3，未声明版本的老服务端按 1 处理。
2. 协商为 v3 时，`GET /v1/lmc/agent/mail?sessionId=…&mailProtocol=3` 只返回最多 20 封未确认邮件，不写 `deliveredAt`。
3. 接收方把看板、配置与 `agentMailInbox[id].phase=projected` 放在同一次严格 metadata CAS 中。失败则不交付、不确认。收件凭据保存在原有加密会话 metadata 中，跨进程重启和引擎切换保留。
4. 普通信件通过 `sendUserTextMessage` 写入会话，配置/审核等控制信件通过 `sendSessionEvent` 写入，不启动模型回合。两者都使用由 mail id 派生的稳定 `localId`，等待现有 v3 会话消息接口返回持久化身份。该接口已有 `(sessionId, localId)` 唯一约束，重复写入返回原记录且不再广播新消息。确认的是入会话存储，不是模型已完成工作。
5. 接收方严格保存 `phase=processed`，再调用 `POST /v1/lmc/agent/mail/ack`，body 为 `{sessionId, ids}`，每批最多 20 个。服务端检查整个批次属于当前账号和收件会话，再对尚未送达的行写 `deliveredAt`。重复确认不改原时间；外来或未知 id 拒绝整批。
6. ACK 成功后保存 `phase=acked`。若响应丢失或这次 metadata 写入失败，下轮仍补 ACK，即使 GET 已经没有邮件。`processed`/`acked` 信件不重复交付。存储已成功但 `processed` 未写入时，重启后复用同一 `localId` 补足确认，不重做配置/看板。

会话消息存储等待默认 15 秒。超时保留原 outbox 与稳定身份，收件仍未确认；同进程重复等待不新增 outbox 项。这里的重取是中心返回同一封未确认邮件，消息存储重试复用同一身份；不会重发原生终端输入，也不改变“未知原生写入不重发”的规则。

收件凭据最多 512 条，只淘汰已 ACK 的最旧项。512 条全是未完成项时停止处理新增信件，继续补 ACK，不清空去重记录。畸形凭据也按保留保护处理。v3 中无法解密或正文无效的信件写一次持久控制提示后确认；密文仍保留在中心，不触发模型。

## 兼容与待刷新

| Agent | 服务端 | 收件方式 | queued / refreshing | 故障保证 |
| --- | --- | --- | --- | --- |
| 新 | 新，协商 v3 | 取信 → 持久处理 → ACK | 继续收件 | ACK 前响应丢失/进程退出可重取；会话消息、看板和配置持久去重 |
| 老 | 新 | 取即标记，老客户端无须理解新字段 | 保持老客户端行为 | 保留旧协议原有故障窗口 |
| 新 | 老，v1/v2 | 不声明 v3，不调用 ACK | 继续暂停 | 保留旧协议原有故障窗口 |
| 老 | 老 | 原协议 | 原行为 | 原协议原有故障窗口 |

四种组合均可按各自协议取信，不因新增字段/接口崩溃。**“老协议取即标记不变”和“四种组合在取信响应丢失时绝不丢信”无法同时成立**：老中心在返回前已经标记，客户端无从恢复该行。完整的故障恢复保证要求双方 v3；不能把兼容性冒充旧端已修复。

channel-key 的能力在 Agent 进程内缓存，服务端必须保持一致版本。禁止在仍有已协商 v3 的 Agent 收件时把中心回退到 v2，或把新旧中心随机混在同一个负载均衡入口。

## 同 ID 额度换手

只有当前执行者对当前 `attempt + dispatch` 的最新有效报告为 `blocked`，且 `blocked` 字段以明确的 `quota` 原因开头，账本才保存 `quotaReport` 证明。后续有效报告或审核会清除此证明。`not quota`、普通 `rate limit`、其他执行者或迟到的旧 dispatch 报告不会授予换手资格。

`assign_task` 在严格 CAS 内再次检查证明、绑定、attempt、预算和截止时间。合格时可派给另一个已经绑定的执行者，记录新执行者并照常累加 attempt（最多 2），保留原 `budgetMinutes` 和 `deadline`。其他 blocked、rejected、进行中任务不能换执行者。看板淘汰、进程重启不会删除证明或重新获得预算。提示词、看板原因和工具门禁采用同一 quota 判定。

## 中枢迁移

迁移先在旧中枢保存 `delegationMigration` 标记并捕获最新账本，标记存在时拒绝旧中枢新增派单和出生执行节点。随后把账本与看板合并到新中枢，再从旧中枢撤销这批执行者、修改执行者绑定，最后授予新中枢并清除旧标记。显式权限选择及既有 autonomy 保留。

同 ID 合并取较大 attempt、较早 deadline、较小 budget。同 attempt 却有不同 worker/dispatch 的记录标为 `conflicted`，后续派发拒绝并要求 DIRECT。并集不得超过 256；非法账本、无法读取旧中枢或容量超限不能按空账本继续。旧账本始终保留，合并失败不能重置预算或产生两个可以派发的所有者。

部分写入失败时保留旧账本与迁移标记，可能暂时无绑定所有者。恢复服务后重试**同一个旧/新中枢对**，已有写入会被识别，不把已被用户另行绑定的执行者覆盖回去。迁移尚未结束时换目的地会拒绝。容量不足或冲突时保持 DIRECT；不要删除账本、改任务 ID 或清标记来绕过限制。旧中枢被删除导致账本不可读时，需要先恢复可核验的旧 metadata，不能猜造期限。

## 角色提示词

模型和思考层级由中枢显式指定，从执行节点所在机器发布的目录选择。未验证的模型/任务组合标实验。提示词保留默认 DIRECT、一个任务一个执行者、一次返工、预算不延长和额度例外，不再写死模型矩阵。实际 SDK/provider 生效与 desired 配置分开核验。

## 服务端上线与回退步骤（未执行）

1. 保存可回退的当前服务端/Agent/App 工件及通常的数据库备份；不得复制真实设备凭据或业务会话数据到实验环境。构建本分支的 wire、服务端、Agent、App。无额外 Prisma migration。
2. 在独立环境执行 [验证记录](verification/lmc-reliable-mail-20261001.md) 中的检查，确认消息 `localId` 唯一约束和现有 v3 消息接口可用。
3. 先按维护流程升级**全部**中心实例。此时老 Agent 仍走取即标记。核验 channel-key 返回 3、v3 GET 后行仍 pending、ACK 才标记、重复 ACK 时间不变。不要向业务会话投实验邮件。
4. 再在真实回合的安全边界升级 Agent，启动新进程以重新协商能力；Claude/Codex 同步支持。App 升级后使用带账本的迁移。观察待确认收件和迁移失败，不清空保护记录。
5. 优先只回退 Agent/App 并保留 v3 中心：旧 Agent 能与新中心通信，但恢复的是旧行为，回退期间保持 DIRECT，暂停迁移和新委派。保留 `agentMailInbox`、`delegationLedger`、`delegationMigration` 及邮件 delivered tombstones，不做数据回退或删行。
6. 若必须回退中心，先停止新委派，在每个接收方安全边界完成已有 `projected/processed` 收件与 ACK，确认无未决迁移，再让 v3 接收进程自然退出/刷新到兼容版本。不得强停活动模型。之后整体回退中心并重新启动接收方以协商 v1/v2；未能排空时保留 v3 服务端并停止回退。旧版本不具备新门禁或故障恢复保证。
