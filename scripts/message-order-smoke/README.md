# 带附件消息确认与实时顺序

启动 `node scripts/message-order-smoke/serve.cjs /tmp/exported-web-build [port]`，用浏览器打开输出的 localhost 地址。加载正式 Metro 产物的真实 `storage.applyMessages`、reducer 和 ChatList；不启动完整应用，不认证，CSP 禁止网络连接。合成附件没有图片字节和凭据，出现占位框符合预期。

按顺序点击“发送图片和文字 → 确认文字 → 确认图片 → 收到新回复 → 收到工具调用”。视图自上向下应为上一轮、附件、用户文字、包含新回复和命令的执行过程。旧 v325 工件会把新回复放在附件和用户文字之前。

再点击“完成本轮 → 重复确认”：最终回复位于同一轮执行过程下方，不出现重复行。点击“重置”后将“确认图片”移到工具调用之后，确认到达时应立即归位；未确认行仍沿用现有时间排序回退。

底部是用于核验的显示顺序与 serverSeq。浏览器验收不向真实模型发送消息，不覆盖服务器持久记录。必须说明其与原设备实发验收的区别。

## HTTP 确认和实时回推竞态

`node scripts/message-order-smoke/serve.cjs /tmp/exported-web-build 0 scripts/message-order-smoke/http-receipt-fixture.js`

此夹具使用真实 `Sync.flushOutbox`、解码/归约路径和 ChatList，只替换加密及服务器传输为合成记录，仍由 CSP 禁止外联。使用比服务器快的发送端时钟，不能靠时间排序碰巧通过。

- “运行 16 项回归”：文字/带附件、两种引擎元数据、没有回推/回复先到/回推先到/重试不再广播；随后重复回推也不得产生重复行。
- “验证补同步与重试”：POST 不跨过未同步消息；不完整确认保留待发批次，重试可完成。
- “真实发送与延迟回推”：从真实 `sendMessage` 进入发送队列，HTTP 先返回，再调用真实 `handleUpdate` 接收同序号回推及下一条回复。旧 v328 的两种引擎均失败；修复后用户“继续”始终位于新回复之前。

结果由底部 JSON 报告；示例 UI 自上而下为“上一轮已结束 → 继续 → 我先补齐恢复，再继续检查”。这是离线真实组件/发送路径验证，不是生产账号的实发验收。
